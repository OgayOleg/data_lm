## 1. О проекте

Сквозной (end-to-end) пайплайн машинного обучения для задачи **бинарной
классификации**, построенный по принципам MLOps: воспроизводимость одной
командой, тесты, линтинг, версионирование данных и модели, CI.

Исследование выполнено на **двух публичных датасетах Kaggle** — это позволяет
проверить, что пайплайн не переобучен под одну задачу, и сравнить поведение
моделей при разном уровне дисбаланса классов.

| | **Telco Customer Churn** | **Bank Marketing** |
|---|---|---|
| **Бизнес-задача** | прогноз оттока клиента телеком-компании | прогноз подписки на срочный депозит |
| **Kaggle** | [blastchar/telco-customer-churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn) | [henriqueyamahata/bank-marketing](https://www.kaggle.com/datasets/henriqueyamahata/bank-marketing) |
| **Записей** | 7 043 | 41 188 |
| **Признаков** | 20 | 20 |
| **Целевая** | `Churn` (Yes/No) | `y` (yes/no) |
| **Дисбаланс** | 73.5% / 26.5% | 88.7% / 11.3% |
| **Лучшая модель** | Logistic Regression (tuned) | XGBoost (tuned) |
| **ROC-AUC (test)** | **0.848** | **0.817** |
| **F1 (test, оптимальный порог)** | **0.637** | **0.528** |
| **Главная особенность** | 11 пропусков `TotalCharges`, сильные категориальные признаки | **утечка данных** в признаке `duration` — обнаружена и устранена |

## 2. Быстрый старт

### Вариант A: одной командой (рекомендуется)

```bash
git clone <url-репозитория> && cd data_lm
bash scripts/run_all.sh          # окружение -> данные -> пайплайн -> тесты -> линтинг
```

### Вариант B: пошагово через make

```bash
make setup       # виртуальное окружение + зависимости
make data        # скачать датасеты (с проверкой SHA-256)
make pipeline    # обучение, CV, тюнинг, оценка, графики, отчёты
make test        # модульные тесты (23 теста)
make check       # линтинг (flake8) + форматирование (black --check) + тесты
```

### Вариант C: через DVC (MLOps-путь)

```bash
pip install dvc
dvc repro        # воспроизводит весь граф: download -> train_telco / train_bank
dvc dag          # граф зависимостей стадий
```

## 4. Методология

### 4.1 Поток данных

```
Kaggle/зеркало ──> data/raw/*.csv ──> очистка ──> feature engineering
      │                                    │
      └── SHA-256 проверка                 └── row-wise, без обучения
                  │
                  ▼
     Stratified train/test split (80/20, random_state=42)
                  │
     ┌────────────┴─────────────┐
     ▼ train (80%)                ▼ test (20%) — не трогаем до финальной оценки
  ColumnTransformer + модель
     │  ├─ 5-fold Stratified CV: 4 модели
     │  ├─ RandomizedSearchCV для лучшей модели
     │  └─ подбор порога решения по out-of-fold F1
     ▼
  Финальная оценка на test → отчёты, графики, модель
```

### 4.2 Ключевое методологическое решение: отсутствие утечек

| Риск утечки | Как устранён |
|---|---|
| Препроцессинг «видел» тестовые данные | всё обучение (`SimpleImputer`, `StandardScaler`, `OneHotEncoder`) внутри `ColumnTransformer`, который обучается **только на train-фолдах**; фиксируется тестом `test_preprocessor_fitted_on_train_only` |
| Утечка целевой переменной в признаке | `duration` (Bank Marketing) удалён из матрицы признаков **до** обучения; эффект измерен отдельным экспериментом (+0.15 ROC-AUC «на бумаге») |
| Подбор порога на тесте | порог подбирается по **out-of-fold** предсказаниям на train |
| Дисбаланс «лечили» только у части моделей | все 4 модели используют `class_weight='balanced'` / `scale_pos_weight` — сравнение честное |

### 4.3 Feature engineering

**Telco Customer Churn**

| Признак | Идея | Обоснование (EDA) |
|---|---|---|
| `num_addons` | сколько из 6 доп. услуг подключено | U-образная связь с оттоком |
| `tenure_group` | сегменты срока жизни (0-1, 1-12, 12-24, 24-48, 48+) | отток резко падает после года |
| `avg_monthly_charge` | `TotalCharges / tenure` | разделяет «дорогой тариф» и «мало месяцев» |
| `charge_growth` | `MonthlyCharges / avg_monthly_charge` | рост цены → риск ухода |
| `has_family`, `is_electronic_check`, `is_new_customer` | бинарные флаги сегментов | EDA-находки |

**Bank Marketing**

| Признак | Идея | Обоснование (EDA) |
|---|---|---|
| `was_contacted_before` | `previous > 0` | контактированные ранее подписываются ~2× чаще |
| `pdays_recency` | корзины давности контакта + категория `never` | `pdays=999` — сентинел, не число |
| `campaign_log` | `log1p(campaign)` | длинный хвост до 56 контактов |
| `season` | сезон из месяца | пики конверсии в марте и сентябре–октябре |
| `macro_stress` | `cons.conf.idx / emp.var.rate` | агрегация макро-сигнала |
| ~~`duration`~~ | **удалён** | утечка целевой переменной |

## 5. Результаты

### 5.1 Telco Customer Churn (7 043 записи, дисбаланс 73.5/26.5)

Метрики на **тестовой выборке** (1 409 записей), порог 0.5:

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| **Logistic Regression** (tuned) | 0.732 | 0.497 | 0.791 | 0.611 | **0.848** | **0.670** |
| XGBoost | 0.759 | 0.534 | 0.730 | 0.617 | 0.835 | 0.647 |
| LightGBM | 0.776 | 0.563 | 0.695 | 0.622 | 0.828 | 0.628 |
| Random Forest | 0.758 | 0.534 | 0.693 | 0.603 | 0.834 | 0.644 |
| Logistic Regression (baseline) | 0.734 | 0.499 | 0.799 | 0.615 | 0.847 | 0.668 |

**Финальная модель:** Logistic Regression (`C=0.1`) с порогом решения **0.58**
(подобран по out-of-fold F1):

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| logreg_tuned @ 0.5 | 0.732 | 0.497 | 0.791 | 0.611 | 0.848 |
| **logreg_tuned @ 0.58** | **0.774** | **0.556** | **0.746** | **0.637** | 0.848 |

> Подбор порога дал **+0.026 F1** и +0.042 Accuracy без переобучения модели.

### 5.2 Bank Marketing (41 188 записей, дисбаланс 88.7/11.3)

Метрики на **тестовой выборке** (8 238 записей), порог 0.5:

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| **XGBoost** (tuned) | 0.901 | 0.690 | 0.227 | 0.342 | **0.817** | **0.492** |
| LightGBM | 0.853 | 0.405 | 0.647 | 0.498 | 0.809 | 0.490 |
| XGBoost (baseline) | 0.849 | 0.397 | 0.649 | 0.492 | 0.810 | 0.487 |
| Random Forest | 0.865 | 0.431 | 0.609 | 0.505 | 0.803 | 0.484 |
| Logistic Regression | 0.835 | 0.368 | 0.647 | 0.469 | 0.801 | 0.456 |

**Финальная модель:** XGBoost (`scale_pos_weight`-aware) с порогом решения **0.19**:

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| xgboost_tuned @ 0.5 | 0.901 | 0.690 | 0.227 | 0.342 | 0.817 |
| **xgboost_tuned @ 0.19** | **0.878** | 0.469 | **0.603** | **0.528** | 0.817 |

> Классический пример: модель с лучшим ROC-AUC имеет **худший** F1 при пороге 0.5.
> Оптимизация порога поднимает F1 на **+0.19** — это важнее выбора между XGBoost и LightGBM.

### 5.3 Проверка гипотезы об утечке данных

Гипотеза: *«`duration` (длительность звонка) недоступен в момент предсказания
и искусственно завышает метрики»*. Проверка одним и тем же LightGBM, CV=5:

| Эксперимент | ROC-AUC (CV) |
|---|---|
| без `duration` (честная модель) | 0.8023 ± 0.0072 |
| с `duration` (утечка) | **0.9504** ± 0.0019 |

**Гипотеза подтверждена:** +0.148 ROC-AUC — «фантомное» качество. Причина:
продолжительность звонка определяется уже по факту разговора, а модель
выучивает тривиальное правило «долгий звонок → подписка». Такая модель
непригодна для продакшена → признак исключён.

### 5.4 Важность признаков (permutation importance по ROC-AUC, top-5)

| # | Telco (logreg) | Падение ROC-AUC | Bank (xgboost) | Падение ROC-AUC |
|---|---|---|---|---|
| 1 | `Contract` (тип контракта) | 0.038 | `nr.employed` (макро: занятость) | 0.047 |
| 2 | `tenure` (стаж клиента) | 0.025 | `emp.var.rate` (ставка занятости) | 0.033 |
| 3 | `tenure_group` *(созданный)* | 0.011 | `euribor3m` (ставка рынка) | 0.012 |
| 4 | `InternetService` | 0.009 | `contact` (канал связи) | 0.011 |
| 5 | `is_new_customer` *(созданный)* | 0.006 | `cons.price.idx` | 0.009 |

**Ключевое различие датасетов:** в Telco важность концентрируется в
**управляемых** признаках клиента (контракт, стаж — на них можно влиять
кампанией), а в Bank доминирует **макроэкономический фон** (~0.10 суммарно),
который компания не контролирует: он определяет, *когда* звонить, а
индивидуальные признаки — *кому*.

> Метрика важности — ROC-AUC, а не accuracy по умолчанию: модель с
> `class_weight='balanced'` переоценивает позитивы, и при перемешивании признака
> accuracy может даже вырасти — получаются отрицательные «важности»
> (см. `reports/REPORT.md`, гипотеза H8).

Интерпретация сходится с EDA: уход определяет **стаж и тип контракта**, а
подписку на депозит — **история прошлых кампаний и макроэкономический фон**.

## 8. Трудности и решения

| Проблема | Решение |
|---|---|
| Kaggle требует API-ключ, недоступен в среде | зеркала датасетов с GitHub, привязанные к коммитам, + обязательная проверка SHA-256 |
| `TotalCharges` приходит строкой с пустыми значениями | `pd.to_numeric(errors='coerce')` + медианная импутация внутри train-фолда |
| `pdays = 999` — сентинел, а не число | замена на `NaN` + отдельный признак давности контакта |
| Скрытая утечка `duration` | обнаружена на EDA, устранена, эффект измерен экспериментом |
| Дисбаланс 89/11 искажал сравнение моделей | единая политика для всех моделей + метрики F1/ROC-AUC/PR-AUC + подбор порога |
| Долгий прогон пайплайна (CPU-only) | `--skip-tuning` для быстрой итерации, кэширование через DVC |
| Некорректный подсчёт ROC-AUC при одном классе | `zero_division=0` и отсутствие `roc_auc` без вероятностей, покрыто тестом |

## 9. Дальнейшие улучшения

1. **MLflow** — трекинг экспериментов (параметры, метрики, артефакты) вместо CSV-файлов.
2. **Feature store / пайплайн ввода** — Airflow/Prefect для регулярного переобучения.
3. **Деплой** — FastAPI-сервис `POST /predict` + Docker (модель уже сериализуется в joblib).
4. **Model monitoring** — контроль дрейфа данных (PSI/KS) и деградации метрик.
5. **Калибровка вероятностей** (`CalibratedClassifierCV`) — важна для решений о порогах и цене ошибок.
6. **CatBoost / стекинг** и **Optuna** для более тонкого подбора гиперпараметров.
7. **Интерпретируемость** — SHAP-значения и частичные зависимости (PDP/ICE).
